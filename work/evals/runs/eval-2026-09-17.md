### What the run does and does not show

**Does show.** On this bundle these four routes are indistinguishable on the
routing slice — all 19/19, all three samples identical on every routing case. The
whole differentiation sits in the error-classification slice, and there only on a
single case. Consistency is high everywhere (≥ 0.9474), i.e. none of them is
flip-flopping.

**Does not show.** This is not a model ranking and must not be read as one
(protocol §5): one bundle, one language mix, one prompt rendering. The slice that
would separate these routes — the failure vocabulary — is the one with a single
shared miss.

### The shared miss: `error-011`

All four routes answer `challenge_required` where the case expects `rate_limited`
(the only failure in every route's error slice).

* Case text: «после серии быстрых запросов yandex_search начал получать
  SmartCaptcha; ошибка помечена как retryable».
* Case evidence: `skills/yandex-connector/SKILL.md` — «Bursts invite SmartCaptcha,
  which surfaces as a retryable rate-limit error».
* Why the models' answer is not defensible here: the bundle's failure vocabulary
  defines `challenge_required` as a login/CAPTCHA/DOM wall that a **human** must
  clear in the scraping profile (`requires_user_action=true`), whereas the case
  describes the burst-driven, self-retryable rate-limit shape our connector
  actually surfaces. The models pattern-matched "Captcha → challenge" without
  reading the catalogue.

Verdict: the case is a legitimate discriminator, not an over-complex one — the
bundle is **not** silently amended. It is flagged here as a v2 candidate for the
"observational" set (protocol §6) precisely because every route misses it the same
way, which makes it useless for separating routes while still being a true test of
catalogue reading.

## Reproduction

```bash
# answer collection is orchestrated (see protocol §4); scoring is deterministic and offline:
uv run python scripts/model_routing_eval.py run \
  --cases work/evals/routing-cases-v1.json \
  --answers work/evals/runs/<route>-2026-09-17.json \
  --model "dashscope2/<route>" \
  --json-out work/evals/runs/<route>-2026-09-17.report.json
```

Re-running the runner on the committed answer files reproduces the reports
byte-for-byte (accuracy rounded to 4 places); no network, no model calls.

## Method notes worth keeping

* One case = one separate call, no batching, system context = the bundle's
  `system_context` only.
* Collection used DSH workflow agents with an explicit `provider`/`model` route;
  each agent read its rendered prompt from a per-case file and wrote the bare
  vocabulary id into a per-sample file. **Sample files on disk are the source of
  truth**: the agent-acknowledgement counter reported by the orchestrator
  under-counted badly (once 1 acknowledged while 14 files were written), so
  progress and completeness were always read from the filesystem.
* Consensus = majority id per case (`pass@majority`), with `consistency` recorded
  separately from correctness, per protocol §3.
