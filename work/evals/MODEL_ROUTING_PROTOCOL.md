# Model routing protocol (v1, 2026-09-13)

Как прогонять model-level routing eval (`work/evals/routing-cases-v1.json`) по
нескольким маршрутам провайдера и как читать результат. Раннер —
`scripts/model_routing_eval.py run`; он **не вызывает модели сам**: ответы
собирает оркестратор (DSH workflow), раннер детерминированно оценивает уже
полученные ответы офлайн.

Канон: `work/v2-research/eval-matrix.md`, строка Routing — «200, 429, 5xx,
timeout, challenge, JSON block, tier-2 failure → transport vs parser drift vs
inconclusive classified correctly», и **«Do not collapse these into one
score»**.

## 1. Что оценивается

Два независимых среза (slice), каждый ≥15 кейсов:

- **routing** — дан запрос пользователя и каталог из 15 скиллов бандла: выберет
  ли модель правильный источник/инструмент. Пограничные пары: «где дешевле»
  (compare-prices) vs «отзывы на одной площадке» (per-source скилл) vs
  «недвижимость/посуточно» (cian-connector) vs «настроить полный mount»
  (marketplace) vs одиночный источник с названием (aliexpress/taobao/…).
- **error-classification** — сценарий сбоя из eval-matrix (429, 5xx, timeout,
  challenge, JSON-блок вида code-7/200-с-404, tier-2 failure, дрейф формы
  ответа, честный null) → один id из словаря отказов (`rate_limited`,
  `timeout`, `transport_down`, `challenge_required`, `parser_drift`,
  `not_found`, `auth_missing`, `bad_request`, `permission_denied`,
  `no_error`, `inconclusive`).

Каждый кейс несёт: `id`, `slice`, `lang`, `query`, `expected`,
`acceptable_alternatives` (допустимые альтернативы), `forbidden` (ответы,
которые проваливают кейс даже при совпадении с каталогом) и `evidence` —
цитату из `skills/*/SKILL.md` / `mcp_core`, которая делает ожидаемый ответ
однозначным по каталогу проекта.

## 2. Изоляция (одинаковый контекст для всех моделей)

- Системный контекст — ровно `system_context` бандла (role + answer_contract +
  каталог скиллов + словарь отказов), **без** скиллов DSH-сессии, без
  additional instructions, без истории. Никакого innego контекста модель не
  видит.
- Промпт кейса рендерится раннером: `render_prompt(bundle, index)` /
  `--prompts-out prompts.json`. Кейс подаётся как «Case i/N» — **id кейса в
  промпт не входит** (префикс `routing-`/`error-` протёк бы срез).
- Один кейс = один отдельный вызов модели (без батчинга нескольких кейсов в
  одном контексте, чтобы ответ на предыдущий не влиял на следующий).
- Температура фиксируется на вызове (рекомендация: default/0, если маршрут
  поддерживает; иначе — записать фактическое значение в метаданные прогона).
- Ответ модели приводится к одному id: оркестратор извлекает первый токен,
  совпадающий с id каталога (раннер сам нормализует регистр/пробелы и требует
  точного совпадения с id; проза вокруг id — на совести извлекающего кода
  оркестратора, в отчёт идёт то, что попало в answers-файл).

## 3. Повторности

- **≥3 сэмпла на кейс** на модель. Каждый сэмпл — отдельный вызов; ответы
  сэмплов не усредняются внутри кейса, а сворачиваются так:
  - `pass@majority` — верным считается ответ, совпавший с expected/альтернативой
    в ≥⌈k/2⌉ из k сэмплов;
  - дополнительно в отчёт попадает `consistency` — доля кейсов, где все k
    сэмплов дали одинаковый id (независимо от правильности).
- Консенсус-ответ модели по кейсу = мажоритарный id; именно он кладётся в
  answers-файл, который скармливается раннеру. Сырые сэмплы сохраняются рядом
  (`…-samples.json`) для разбора расхождений.

## 4. Формат обмена с оркестратором

Answers-файл (вход раннера) — JSON, одна из двух форм:

```json
{"routing-001": "compare-prices", "error-001": "rate_limited"}
```

или обёртка с метаданными (раннер понимает обе):

```json
{
  "model": "dashscope2/qwen3.8-flash",
  "run_id": "2026-09-13T15:00Z",
  "samples_per_case": 3,
  "answers": {"routing-001": "compare-prices", "...": "..."}
}
```

Запуск:

```
uv run python scripts/model_routing_eval.py run \
  --cases work/evals/routing-cases-v1.json \
  --answers work/evals/runs/<model>-<date>.json \
  --model "dashscope2/<model>" \
  --json-out work/evals/runs/<model>-<date>.report.json
```

(answers также читаются из stdin: `--answers -`). Сгенерировать промпты для
workflow: `--prompts-out work/evals/runs/prompts.json` (раннер выйдет сразу
после записи).

Маршруты для мульти-прогона (пробированы 10.09, **требуется ре-проб перед
прогоном**): dashscope2/{qwen3.8-max-0902, qwen3.8-flash, ZHIPU/GLM-5.3,
ZHIPU/GLM-5.3-Flash, kimi/kimi-k3, deepseek-v4-pro-0813}.

## 5. Метрики — не схлопывать в одну оценку

Отчёт раннера содержит и `accuracy` по всему бандлу, и `per_slice` — читать
нужно **per_slice**:

| метрика | что значит |
|---|---|
| `per_slice.routing.accuracy` | доля верных routing-кейсов (полный знаменатель) |
| `per_slice.error-classification.accuracy` | доля верных классификаций сбоя |
| `accuracy_answered` | то же, но по отвеченным кейсам (пилоты/частичные прогоны) |
| `consistency` (из п.3) | стабильность выбора, отдельно от правильности |
| p50/p95 латентность на вызов | измеряет оркестратор при сборе ответов; в отчёт прогона пишется рядом с accuracy |
| `missing_ids` / `complete` | полнота прогона: `complete=false` ⇒ прогон невалиден как итоговый |

Запрещено: заявлять «модель A лучше B» по одному числу. Хорошая медиана не
компенсирует провал на `inconclusive` vs `parser_drift` (ложный «дрейф» там,
где транспорт не отвечал, — это ложная тревога для healtcheck-контракта) или
систематический увод «где дешевле» в `marketplace`.

Пороги (v1, для мульти-прогона): routing accuracy ≥ 0.90 и error-classification
accuracy ≥ 0.85 на консенсус-ответах при `complete=true`; ниже — маршрут не
назначается на соответствующую роль без ручного разбора.

## 6. Как интерпретировать расхождения

- **expected vs alternative.** Альтернативы закладываются только там, где
  каталог проекта genuinely допускает две трактовки (например, routing-019:
  `compare_sources` из compare-prices vs `marketplace_sources` из marketplace;
  error-010: 429→403 на глубокой пагинации Avito — `rate_limited` или
  `transport_down`, скилл называет ожидаемым оба). Провал по alternative —
  сигнал не о модели, а о том, что кейс переусложнён: такие кейсы помечаются в
  отчёте и переносятся в v2 как «наблюдательные».
- **Расхождение между моделями на одном кейсе** — не автоматически «модель
  виновата»: сначала свериться с `evidence` кейса. Если разумная модель
  систематически отвечает иначе и её ответ защищаем цитатой из SKILL.md —
  правится кейс (датированная правка в бандле, не молчаливая), а не оценка.
- **Расхождение между сэмплами одной модели** (`consistency` < 1) важнее
  единичного провала: нестабильный выбор на пограничье («где дешевле на WB или
  Ozon») — аргумент против роли, где этот маршрут видит пользовательские
  запросы напрямую.
- **`forbidden`-провал** — самый тяжёлый сигнал (например, `mpstats-connector`
  на bare price check или `parser_drift` на честный null): это не «не угадала»,
  а выбор, который ломает контракт бандла (платная аналитика вместо бесплатной
  карточки; ложная тревога дрейфа на валидных данных). Такие провалы
  разбираются поштучно в dated-отчёте прогона.
- Исторические результаты — в датированных отчётах в `work/evals/`
  (`runs/<model>-<date>.report.json` + сводка `multi-YYYY-MM-DD.md`), никогда
  не в безусловных правилах роутинга.

## 7. Ограничения раннера

- Раннер детерминирован: одинаковый answers-файл ⇒ байт-в-байт одинаковый
  отчёт (округление accuracy — 4 знака). Никакой сети, никаких вызовов LLM.
- Раннер не измеряет латентность (её знает только оркестратор, который делал
  вызовы) и не валидирует, что ответы собраны честно (изоляция — на стороне
  собирающего).
- `scripts/routing_eval.py` остаётся отдельным детерминированным контрактом
  (keyword-route фикстуры) и этим раннером не заменяется.

## 8. Датированные прогоны

### 2026-09-17 — сокращённый мульти-прогон (`runs/eval-2026-09-17.md`)

Собраны **полностью 4 маршрута** (по 3 сэмпла на кейс, `complete=true`):
`qwen3.8-flash`, `qwen3.8-max-0902`, `ZHIPU/GLM-5.3`, `deepseek-v4-pro-0813`.
Все четыре проходят пороги (routing 1.0, error-classification 0.9474) и **все
четыре проваливают один и тот же кейс `error-011`** (`rate_limited` →
`challenge_required`), разобранный в отчёте; бандл молча не правился, кейс помечен
кандидатом в «наблюдательные» v2.

Два маршрута (`ZHIPU/GLM-5.3-Flash` — 42/114, `kimi/kimi-k3` — 16/114) остановлены
троттлингом провайдера: на этих роутах падает около половины агентов, тогда как
qwen- и deepseek-роуты отдают 57/57 в одном чанке. Прогон остановлен решением
владельца — это **сокращённый прогон, а не полный протокольный свип**.

Правило, действующее до следующего полного прогона: **частичные маршруты
(`complete=false`) не используются для назначения на роль**; они остаются в отчёте
как запись о состоянии, чтобы следующий прогон продолжил, а не начинал заново.
Порог «≥5 маршрутов» остаётся целью следующего прогона.
